# Step 3: Implement ONE Ticket

Claim one issue from the `READY` set produced by Step 2, implement it,
and commit. **Do not push** in loop mode (batch handles that in Step 3.7).

`_lib.md` helpers used here: `issue_body`, `issue_title`,
`branch_for_issue`, `issue_to_item_id`, `set_item_status`,
`append_failure_comment`.

## 3a: Claim

appee is solo workflow — no remote-lock dance. The "claim" is moving
the board item's Status to `In progress`.

1. **Single-ticket mode**: `$ISSUE_NUM` is already set (parsed from
   `$ARGUMENTS` via `parse_issue_num`). Fetch the issue:

   ```bash
   if ! gh issue view "$ISSUE_NUM" --repo "$APPEE_REPO" --json number > /dev/null 2>&1; then
     echo "ERROR: issue #${ISSUE_NUM} not found in ${APPEE_REPO}"
     exit 1
   fi
   BODY=$(issue_body "$ISSUE_NUM")
   TITLE=$(issue_title "$ISSUE_NUM")
   LABELS=$(issue_labels "$ISSUE_NUM")
   ```

2. **Loop mode**: pop the highest-priority Ready item from Step 2's
   queue. If the queue is empty:
   - Run Step 5b (triage) once.
   - Then enter the wait loop:
     ```
     while true:
       if .claude/b-start-stop-signal exists: exit pipeline
       if .claude/b-start-fresh-mode missing: exit pipeline
       re-run Step 2 (fetch_board → flatten_board → classify)
       READY_COUNT=$(echo "$ready" | grep -cE '^[0-9]+$')
       if READY_COUNT > 0: break  # claim
       echo "No Ready issues — sleeping 60s"
       sleep 60
     ```
   - **NEVER exit the pipeline on empty board** — only stop signal /
     fresh-mode removal can end the loop.

3. **Move to In progress** — board status update (idempotent):

   ```bash
   ITEM_ID=$(issue_to_item_id "$ISSUE_NUM")
   if [ -z "$ITEM_ID" ]; then
     echo "WARN: issue #${ISSUE_NUM} not on board — adding it now"
     ITEM_ID=$(gh project item-add "$APPEE_PROJECT_NUM" --owner bradyoo12 \
       --url "https://github.com/${APPEE_REPO}/issues/${ISSUE_NUM}" \
       --format json --jq '.id')
   fi
   set_item_status "$ITEM_ID" "$STATUS_IN_PROGRESS"
   ```

   Optionally drop a one-line comment for audit trail:

   ```bash
   gh issue comment "$ISSUE_NUM" --repo "$APPEE_REPO" \
     --body "> **In progress (`date -u +%Y-%m-%dT%H:%M:%SZ`)** — worker \`$WORKER_ID\`" \
     2>/dev/null || true
   ```

## 3c: Implement

Read the issue body in full. Pay special attention to:

- **원본 요청** — verbatim user input. Your implementation must address
  what the user actually asked for, not your interpretation.
- **문제 정의** — the user-facing motivation. If your implementation
  doesn't address this, you're doing the wrong thing.
- **범위 (Scope)** — explicit in/out. Don't expand scope. (Memory:
  `feedback_minimal_implementation.md` — 가장 작은 한 조각만.)
- **성공 기준** — each item has `검증 명령` / `통과 기준` / `검증 대상`.
  Your implementation must make every `검증 명령` PASS per its
  `통과 기준`.
- **구현 가이드** — direction + concrete file paths from the ticket
  drafter. Use those paths verbatim.
- **UI 목업** — if present, this is the visual target. Implementation
  should match it (modulo spacing/label copy — verify with Playwright
  per memory `feedback_ui_verify_playwright.md`).
- **Issue comments** — Deploy-Retry failure context from previous
  attempts is posted as **issue comments** (not body appends). Read
  every comment before starting:
  ```bash
  gh issue view "$ISSUE_NUM" --repo "$APPEE_REPO" --comments \
    --json comments --jq '.comments[] | .body'
  ```
  The "DO NOT repeat the same fix" rule depends on the implementer
  actually reading prior failure notes.
- **Open questions** — if blocking, surface in chat (Korean) and ask.
  Don't invent answers.

## 3d: Verify locally before committing

Run the project's checks before staging:

```bash
# From $WORKTREE_DIR (slot-local node_modules)
pnpm typecheck
pnpm lint
```

If the issue's 성공 기준 listed specific `검증 명령` entries
(`pnpm playwright test ...`, `curl ...`, `pnpm --filter ... drizzle-kit generate`,
etc.), run those too before committing.

If anything is red, don't commit. Either fix or surface the failure +
ask the user.

## 3e: Commit

Stage **specific files** — never `git add -A`:

```bash
git add apps/console/src/<changed-files> apps/console/drizzle/<migrations>
```

Commit via heredoc with the issue number (Closes-style) in the subject
+ Co-Authored-By trailer. Match the existing appee commit style
(slice-prefixed):

```bash
git commit -m "$(cat <<EOF
[Slice ${SLICE_N}] <ticket-code or E${EPIC}-${N}> <imperative summary> (#${ISSUE_NUM})

<one-paragraph rationale — the "why" not the "what">

Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>
EOF
)"
```

> The `#${ISSUE_NUM}` in the subject auto-links to the GitHub issue on
> the commit page. The PR body (Step 4) carries the actual `Closes #N`
> directive that closes the issue on merge.

Recent appee commits for style reference:

```
[Slice 0] E3-2 2.B: apps table schema
[Slice 0] E3-2 2.A: Drizzle scaffold (config + db client + empty schema)
[Slice 0] E1 1.D: deploy is now auth-gated, build records the user
```

## 3f: Record + return

Append to `BATCH_ISSUES` (loop mode) so Step 3.7 can build the PR body:

```bash
T_TITLE=$(issue_title "$ISSUE_NUM")
BATCH_ISSUES+=("${ISSUE_NUM}|${T_TITLE}")
```

→ Return to `b-start.md` Step 3.5 (batch check) or Step 4 (single-ticket
push + PR).

## 3-cleanup: On failure

If anything in 3c–3e fails irrecoverably:

1. Move the board item back to **Ready** (single-ticket mode) — so the
   next cycle re-picks it:
   ```bash
   set_item_status "$ITEM_ID" "$STATUS_READY"
   ```
2. Drop a comment with the failure summary:
   ```bash
   append_failure_comment "$ISSUE_NUM" "> **Step 3 aborted (`date -u +%Y-%m-%dT%H:%M:%SZ`)** — see failure log above. Board status reset to Ready."
   ```
3. `git reset --hard origin/main` to drop any partial commits (in
   single-ticket mode the branch is per-issue so `--hard` is safe; in
   loop mode use `git reset HEAD~1` to drop only this issue's commit).
4. Surface the failure in chat (Korean).
